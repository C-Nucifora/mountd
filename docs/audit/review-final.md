**RF-1, medium: launchd recovery can treat an unsettled mutation as complete.**

Evidence:

- [launchd.rs:123](/home/christian/Documents/dev/mountd/src/launchd.rs:123), lines 123 through 150, saves the result of the mutating command but checks `is_loaded()` before examining that result. An absent service makes `bootout` return success, and a present service makes `bootstrap` return success, even if the saved error is `CleanupPending`.
- [mountcmd.rs:363](/home/christian/Documents/dev/mountd/src/mountcmd.rs:363), lines 363 through 376, deliberately returns `CleanupPending` while the supervisor still waits for its child. This is explicit evidence of incomplete cleanup, not an ordinary command failure.
- [launchd.rs:225](/home/christian/Documents/dev/mountd/src/launchd.rs:225), lines 225 through 265, permits replacement after the first bootout, and rollback after another bootout. The rollback bootout returns immediately when its initial snapshot reports absence. No state records an earlier outstanding bootstrap request.
- [mountctl.rs:135](/home/christian/Documents/dev/mountd/src/bin/mountctl.rs:135), lines 135 through 144, returns from install/uninstall without draining command supervisors. Unlike the daemon's shutdown path, CLI runtime teardown can therefore discard a pending supervisor.

A credible failure sequence starts with an absent service. Bootstrap submits a request, then times out before its outcome is settled. The first inspection still reports absence. Recovery calls bootout, whose initial inspection also reports absence, so it does not submit a removal request. A fresh install deletes the plist; an update restores the old plist and may restart the old registration. If the submitted bootstrap subsequently takes effect, the registered job and the restored files no longer represent the same installation. The corresponding bootout sequence reports failure while the old service is still visible, then leaves the installation stopped when the delayed removal completes.

There is also a narrower, directly demonstrable branch error. Inject `Err(CleanupPending)` from a mutating command while retaining its synthetic completion gate. Return the desired state from `print`. Both wrappers report success while cleanup is explicitly outstanding. Install/uninstall can then mutate files and finish the CLI. This does not require an arbitrary background dependency or a pathname attack.

Expected behavior is to preserve uncertainty until the earlier mutation is settled. A current service-presence snapshot must not erase `CleanupPending` or prove that an outstanding request cannot act later. Do not overwrite/remove recovery files, issue conflicting mutations, or report a completed transaction on that basis.

The smallest correction is to preserve a distinct unsettled outcome from mutating launchctl calls, short-circuit ordinary rollback on it, and retain the attempted plist plus the previous bytes for recovery. Keep the CLI's supervisor alive until owned client cleanup finishes. For a timed-out client that has already reaped, only promote inspection to a settled result if the native launchd contract establishes that the inspection orders after the submitted mutation. Otherwise return an explicit uncertain outcome and retain recovery information. A longer timeout or repeated presence snapshots alone does not establish that ordering.

Add a disposable regression that holds mutation completion behind a gate, supplies the old state to inspection, and releases the mutation only after recovery would otherwise have acted. Separately inject `CleanupPending` with the desired state already visible and assert that success/file replacement is refused while the gate remains held. These are proposed tests, not executions by this reviewer. The exact late-request behavior of native launchd remains unexecuted; the unconditional loss of `CleanupPending` is visible in the Rust source.

The existing [portable-native.py:63](/home/christian/Documents/dev/mountd/tests/portable-native.py:63) mutates its loaded marker before either failing or delaying its reply. Its delay cases therefore exercise a completed mutation followed by a lost reply. They do not establish settlement of a still-pending mutation. The menu installer's analogous post-error inspection also lacks native ordering evidence, but it has no Rust `CleanupPending` path. I am not counting that platform question as a second finding.
